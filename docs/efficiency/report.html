Where formuls spends its CPU

I profiled the running instrument before changing anything. Half the machine was the synth, and a sixth of a core was being spent at idle on nothing but message plumbing. Both are now substantially cheaper, and the sound is unchanged to −74 dB or better — including the pitch slide, whose start and end frequencies are bit-identical.

Snapshot, not a live document. This describes efficiency-dev as merged into juce-port at e360ce7, measured 3 September 2026. The branch has moved on since: 480cc97 removed the OTT, digitaliser, widener and limiter from the master bus, and d33e554 routed the reverb back into the main stereo output. Everything about the synth and the control-rate throttles still holds — those are untouched by that work. The one measurement it invalidates is flagged below where it appears.

The finding that set the priorities

Half the machine was the synth

Sampling the running patch for 20 seconds with DSP on, three paired runs, normalised by each run's own non-idle work so the scheduler's slack cancels out: formuls~ — the Faust synth in fsynth.lib — accounted for 50% of every cycle the app spent doing work. Its powf, sinf and tanhf calls alone were about 15% of the total.

Separately, with DSP switched off, the patch still burned 17.4% of a core doing nothing at all. That turned out to be two master throttles — one at 100 Hz, one at 25 Hz — fanning out to 427 instances of f.seq.automater, each of which rebuilt a message, pushed it through a 23-selector route, and re-broadcast it internally.

Getting to the floor

The throttle work happens whether or not anything is listening. Two changes took it most of the way to the cost of not running the throttles at all — the reference line below.

Applied — each independently verified

The six changes

  1. 01

    Per-voice powf, sinf and tanhf, removed

    Each of the 20 voices ran three powf(), one sinf() and one tanhf() on every sample. The ADSR's x^2.7 curve is now a 1024-point interpolated table; pow(2, oscsliderange) moved to before its sample-and-hold so Faust hoists it to control rate, which is bit-exact; sin(pi*x) and tanh(100*sin(pi*x)) became tables in fosc.lib.

    Per-sample calls: pow 66→28, sin 24→5, tanh 22→2.

    +18% synth throughput
  2. 02

    Automaters read the master throttles directly

    Every 100 Hz tick previously ran about ten message dispatches per automater: a receive, a message box, t a, a spigot, an outlet crossing, a 23-selector route, then a send and two more receives. The three consumers now bind the global symbols directly.

    17.4% → 7.9% of a core at idle
  3. 03

    The automater LFO runs at control rate

    It generated its waveform with [osc~] and read it with [snapshot~] on a throttle tick — 48,000 samples a second computed so that 100 could be looked at, times 427 instances. Now a phase accumulator clocked by the same throttle.

    854 signal objects removed from the DSP graph
  4. 04

    Broken objects, and the dead branches they fed

    433 “couldn't create” errors on every start, from two objects someone had disabled by typing a hyphen in front of the class name — -r $0-ext-mod in 427 places, -f.util.oscformatxy in six. Pd still tries to create them, fails, and logs. Both are gone, along with a branch that terminated in a [+] wired to nothing.

    startup console: 876 lines → 10
  5. 05

    The automation playback clock binds the throttle directly

    The last big relay, and 75% of what remained. Every automater built a paramthrottle bang; f.seq.record matched it last of fifteen route selectors; it ended at a [spigot 0] that is shut unless automation is actually playing back. The abstraction's own paramthrottle inlet still works — both paths now meet at a [t b].

    7.9% → 3.8% of a core at idle
  6. 06

    The pitch-slide curve uses the same table

    Held back at first, because the sample-by-sample difference in the slide scenario looked large and I could not show it was harmless. It is — what moves is oscillator phase, not pitch or level. The deciding question was whether the slide's start and end frequencies move, and they don't: ba.tabulate evaluates x^2.7 at the range ends, so entry 0 is exactly 0 and entry 1023 exactly 1, and at those inputs the interpolation fraction is exactly zero.

    Measured: diff = 0 at both endpoints. The path between them moves by at most 0.02 cents, at the widest slide range — about 300× below the just-noticeable difference, and well inside the resolution at which a by-ear exponent was chosen.

    +7% more, on top of commit 1

Holding the rest of the app constant, that is the synth itself costing 17% less. Evidence

How the behavioural changes were checked

Two of the five changes alter a number somewhere. Neither was argued from first principles — a change that is algebraically identical can still move the sound, and a change that fails a sample-by-sample diff can still be perfectly transparent.

The Faust rewrite

Seven parameter scenarios rendered from both versions and compared: ADSR polyphonic, waveshape sweep, sustained mono, FM with pitch slide, noise, the full FX chain, and an AM oscillator sweep. Worst case −74 dB error relative to signal and RMS-envelope agreement −71 dB or better, in the six scenarios without a pitch slide.

The pitch slide

The one place the trajectory could have moved. Endpoints measured at diff = 0, so the slide still starts at exactly the carrier frequency and still tops out at exactly o1f × (1 + 2^oscsliderange). Worst deviation along the path is 7.2e−7 of full scale — 0.0007 to 0.0196 cents depending on slide range. Scenario 4 below is the only one this changes, at −28.4 dB sample-domain but −59.1 dB RMS envelope: the signature of accumulated phase, not of a change in what is heard.

The LFO

Old and new LFO canvases extracted into standalone patches and driven identically inside the real _main.pd for five seconds. Output range identical at [0.2273, 0.7726]; rate identical at 4.0 cycles in 5.0 s; and at one tick of lag the maximum difference is 0.00093, or 0.17% of modulation depth. The one-tick offset is inherent — [snapshot~] returns the previous block's last sample, while the accumulator advances in the current tick.

The playback clock

Both deliveries run side by side into identical [i 0]→[+ 1] counters for 399 ticks. The captured sequences are byte-identical.

B — Lower the polyphony

option-B-polyphony-12.patch

POLYPHONY is 20. Every voice is computed on every sample and then multiplied by poly(i,c), which is zero for all but the current voice unless the polyphonic checkbox and the ADSR are both on — so in three of the four modes, 19 of 20 voices are computed and thrown away. Faust cannot skip them; only the constant can change.

C — Wire up the trigger that never fires

option-C-wire-up-automater-trig.patch

A live bug, not an optimisation. f.seq.automater creates f.seq.automatermessage $1 with one argument, but the abstraction uses $2: [r $2-trig] expands to [r 0-trig], a symbol nothing sends. It gates a [spigot] that therefore never opens, so trig bang never reaches the automater from $1-automater-trig. Passing $2 through is what the code looks like it wants.

Why I left it: this switches on dormant behaviour rather than speeding anything up. Turning it on with you offline seemed like the wrong call — a comment in the patch records the finding either way.

Investigated, deliberately left alone

Things that looked promising and weren't

  • Master-bus effects are already cheap. Measured individually: reverb 0.46%, repeater 0.27%, OTT 0.14%, digitaliser 0.06%, widener 0.06%, limiter 0.02% of a core. Wrapping them in [switch~] to bypass them would buy about 1% and risk graph-rebuild clicks.Superseded. Four of these six effects — OTT, digitaliser, widener and limiter — were removed from this branch in 480cc97, after these numbers were taken. The figures stand as a record of what the full chain cost; they no longer describe the master bus as it is built today. The conclusion is unaffected, and now more so: what remains is cheaper still.
  • Three half-wired [pipe 30] objects in f.util.oscinparse. Five [sel 1]→[pipe 30] chains, of which two have output connections and three do not. Two of five being wired reads like an edit that stopped halfway rather than dead code, so it is reported rather than removed. Runtime cost is negligible.
  • f.seq.record carries a TEST_UNIT___ panel — a manual test harness with GUI widgets — in all 427 instances, about 7,700 objects. It costs allocation and a little load time and nothing per tick. Removing it would lose a development affordance for no measurable gain.
  • A genuine double-selection in fsynth.lib. Line 18 wraps the carrier frequency in si.interpolate(adsron) over a value that ox() has already selected on adsron. Removing it measures at 0% and perturbs how Faust factors the surrounding expression — it starts emitting A*(P+1) where it emitted A + A*P, which rounds differently and drifts the oscillator. Left as written.

Read this before re-running anything

One measurement trap

pd -nogui -noaudio with DSP on is not a valid way to compare DSP cost. Pd's polling scheduler spends whatever slack it has spinning, so making the DSP cheaper shows up as more measured CPU.

Verified directly: swapping in the faster formuls~ raised the number, while faust2bench measured the same binary 26% faster. Every DSP claim on this page therefore comes from faust2bench or from sample profiles normalised by total non-idle work. The dsp=0 runs behave correctly and monotonically, and are where the control-rate numbers come from.

Two smaller traps in the same harness

  1. [print] output is discarded under -nogui, even with -stderr, while pd_error output still appears. Capture values with [textfile] and a write <path> cr message instead.
  2. Piping Pd's console into head kills it with SIGPIPE partway through loading, so loadbangs and delays never run and the patch looks broken. Redirect to a file.

And in the file format itself: a message box needs \;. An unescaped ; truncates the record and silently breaks every following connection in that canvas.

Tooling to reproduce all of it is in docs/efficiency/tools/ — a Pd patch parser, a structural editor that renumbers connections while preserving untouched records byte for byte, a runtime object census that expands the abstraction tree, and a Faust A/B architecture file with sample-domain and spectral comparison scripts.
